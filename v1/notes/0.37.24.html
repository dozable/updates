doz 0.37.24

New and updated recipes no longer need a doz release (issue #348; loop 627, step 15; the first half of 617.B11). Owner 2026-10-15: "backlog decoupling the known recipes from the cli build (i think this enables our community builds use-case)"; 2026-10-26: "yes start 15".

  • One signed catalogue: Dozable's recipe data (agents, providers, gateways, known entries, tags, icons) can be published as a catalogue at https://updates.dozable.com/v1/recipes.json, signed with the update key under its own domain-separated message, so a feed signature can never pass as a catalogue's or the other way round.
  • When it applies: the host checks at most hourly (a conditional GET; "not found" is normal and quiet) and caches a catalogue that verifies. It takes effect at the host's next start, and every doz process reads its recipes once, at start — nothing changes under a running process, and commands use the same recipes as the running host.
  • What it may never do: replace this build's Claude Code, pi or Codex; apply in part (a bad signature, a changed file or any failed check ignores the whole catalogue); apply when it needs a newer doz, or was made from older recipes than this build carries (which also blocks going back). Statistics count only agent ids this build knows the Worker accepts.
  • The embedded set stays as the offline fallback and the floor; development builds and guarded runs always use it. doz doctor gains a recipes line.
  • Publishing: make publish-recipes [MIN_DOZ=] [DRY_RUN=1] [PUSH=1] signs with the keychain key. No catalogue is published yet — the first live publish waits for the owner's word.
  • Tests: 15 new catalogue tests (signing, replay, merging, refusals); make test-recipe-catalogue 24/24 (publish with a throwaway key → a real host fetches → a new process uses it; a changed file is refused and the old catalogue kept); the full suite (1300, 0 failed); make recipe-check RECIPES=grok from a catalogue-provided copy.
