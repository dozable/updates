Your own recipes, community catalogues, and the community check (issue #263; loop 627, step 16; the second half of 617.B11). Owner 2026-10-15: "backlog decoupling the known recipes from the cli build (i think this enables our community builds use-case)"; 2026-10-26: "ok do 16 next and also allow the end-user to create their own with the option to verify as meeting the minimum requirements for a community recipe".

  • Your own recipes: doz recipe new [--from RECIPE] | add FILE | ls | show | check | trust | rm — a schema: 2 YAML in <settings>/recipes/mine/, used on this Mac with no release, catalogue or key, and labelled "yours" everywhere a recipe is shown (doz search, doz try, the plan, Quick try, New Sandbox).
  • The minimum requirements for a community recipe: a closed list of 13 (the schema read strictly, every validator, none of Dozable's ids, not built-in, maker/link/licence/description filled in, plain text only, every download pinned with its integrity, a guide and a check turn, no credential, no quiet hosts, no hidden vendor hosts, no Dozable mark or family). doz recipe check prints them item by item and one verdict; every recipe that is not Dozable's must pass them or it is not used. A pass is recorded with the file's sha256.
  • The full check: doz recipe check --full builds and tries the recipe for real from the installed doz (no Python): a scratch store, fake keys, a Swift stand-in model provider — build at the pin, a fresh Locked try, the first screen, verify, the check turn, the guide's steps, no key in the guest, the leak guard. The agent's status reports, web ports and other model sources stay make recipe-check's.
  • Community catalogues: doz recipe source add URL --key KEY — the key's fingerprint is shown and confirmed before anything is fetched; Dozable's own key is refused as a source key; 652's format as doz-community-recipes, signed with the publisher's key, refreshed hourly, applied at the next host start. A tampered file or a clashing id refuses the whole source. Dozable's ids always win; the first source added keeps an id. The CLI asks once per community recipe version before a sandbox is made. Removing a source never breaks a sandbox made from it.
  • Statistics: nothing is counted for recipes that are not Dozable's.
  • Publishing: make publish-recipes COMMUNITY=1 signs a community catalogue with another key and checks it with doz recipe source verify first; nothing is pushed without PUSH=1. No community catalogue is hosted by Dozable.
  • Tests: the full suite (1317, 0 failed); make test-community-recipes 44/44; 652's make test-recipe-catalogue 24/24; doz recipe check --full on a personal copy of OpenCode; the dashboard's labels in headless Chrome at 1440/390 px, light and dark.
