Production sound (issue #217; loop 627, step 27). Owner 2026-10-27: "ship 667".

  • A setting per sandbox: sandbox.audio = off (the default), speakers or on, chosen at create (doz create --sound, --audio still means on, audio: in doz_project.yaml, New sandbox › Bridges › Sound). Afterwards a sandbox moves only between speakers and on. It is shown on the Home, the header chip, the inspector, doz doctor and doz-sound.
  • The microphone, only once macOS has said yes: a sandbox's VM gets the Mac's microphone only when macOS has already allowed it; until then it records silence and Virtualization never asks. That removes 604's two faults: the VM stopping while macOS's question was open, and a recording stuck after Allow. The permission check lives in Microphone.swift, the one file allowed to use AVFoundation, behind a test seam (DOZ_TEST_MICROPHONE).
  • When doz asks: sandbox.microphone_ask = first_recording (the default) or first_start. At first recording, a light watch inside the sandbox notices a capture stream opening and the host asks macOS about 0.8 s later. That recording stays silent, and doz says so in the sandbox's terminals, the dashboard, doz-sound and its Home: Shut Down and Start gives it the Mac's microphone.
  • Fixed: a wake with a different microphone source. The source is part of a VM's saved state, so a restore with another one failed and the sandbox cold-booted. It is now recorded with the sandbox and every restore keeps it; a new answer from macOS applies at the next cold boot.
  • The sound kernel, built from source: Guest/sound-kernel/ holds the recipe (kata 6.18.15-186 plus the ALSA and virtio-snd options), its config, kata's patch and PROVENANCE.md with the written source offer. make sound-kernel builds it twice in a throwaway VM and checks the bytes against the pin (vmlinux-6.18.15-186-sound2, sha256 8d71cc61…); a CI job on the Dozable runner does the same and publishes it (green twice, about 10 minutes). Public builds still carry no kernel, so sound stays off there for now.
  • Re-measured: 604's stream stall after hibernate or wake no longer happens (three runs), so it has no fix. The ticks and leading silence come from the Mac's input path, not the guest.
  • Tests: the full suite (1380, 0 failed); make audit; make docs-drift-check; the VM proof (playback, a recording through the seamed microphone, hibernate → restore) green three times; the first-recording proof green twice; the microphone source across a restore both ways.
