Chat, steps 9–10: the daemon runs the chat server; the first doz chat commands (early, hidden from doz --help) (issue #444; chat loop 698; the owner's reorder: "so i can see something ASAP"). The owner tried the dev build with the commands and with a separate terminal client over the private socket: "test of doz-dev chat and agent-chat works".

  • The daemon runs the chat server as a child process on this Mac only (127.0.0.1), when chat.enabled is on (off by default; set on this Mac only, never from the dashboard). It restarts the server if it stops (never after a settings fault), stops it with the daemon, leaves no orphan if the daemon is killed, and follows an upgrade. Chat on keeps the daemon running, like a running session. doz daemon status and doz doctor say how it is. Settings: chat.enabled, chat.page_port (8790), chat.line_port (8791).
  • You are reached only through a private socket in the store: its folder is yours alone, each connection's user is checked, and a fenced session is denied it. There is no token for you, so none can be taken, and nothing on a network port can act as you (the page port answers 403 outside the agents' calls; the line port always needs a token).
  • doz chat: on [--name], off, status, add NAME, remove, who, token NAME --new, rooms, room NAME @member…, send ROOM TEXT, read ROOM [--last N] [--follow]. An agent added this way collects its messages with its own token, which is shown once (or written to a file), kept only as a hash, and never appears in a log, a status or a command line. doz chat status --json gives the socket's path, so another program you run can use it.
  • Not yet: webhook bots, Claude Code sessions as participants, the chat view in the dashboard, import. The group is hidden from doz --help until the dashboard view exists; doz chat --help lists it.
  • Fixed, from 0.51.0: a settings line under an old name (workspace.ignore_mode, workspace.view) was warned about on every command even after the new name was set; the old line is now dropped once its new name has a value. Two fence checks that could never fail (the tool they used reports failure even on a successful connection) now make a real connection, with a control.
  • Tests (re-run by the orchestrator): make test 2015 / 0; make test-chat-conformance 159 / 159; make audit; make docs-drift-check; test-cli-chat, test-cli-daemon, test-cli-alwayson, test-cli-fence and test-vm-upgrade ALL PASS. make test-cli: the 2 failures that predate this release, plus 6 rows of the browser-callback part that failed in that one run and passed when the browser suite was run again alone (make test-cli-browser ALL PASS) — an intermittent failure, not seen in the two full runs earlier today.
