doz 0.37.23

A wake is done as soon as the sandbox runs (issue #345; loop 627, step 32a, following 650). Owner 2026-10-26: "are we still sub-second restore ?", then "yes move them off the critical path as a follow-up feature".

  • What a wake waits for now: the guest running, its clock re-synced, its folders re-mounted and the snapshot deleted. The guest fixes, the deckhold refresh, the tools check and the memory balloon run right after, in the background — never failing the wake (a failure is a note).
  • Still in order: Sleep, Hibernate, Shut down, a restore point and quitting the host wait for those steps; a sleep or shutdown that arrives meanwhile skips what is left (the next wake does it again). Opening a session or running a command waits for them too, so a new session always has what they install.
  • The boot log records the background part as one step after the wake.
  • Measured: the host's own time after Apple's restore fell from ~260 ms to 13–36 ms; the first wake of a batch took 696 ms in the host. Six hibernated sandboxes one at a time: 8.1–9.2 s instead of 12.5 s; three at a time 3.9–4.1 s; all at once 3.2–3.6 s. A wake after a host restart spends ~55–90 ms around the restore — the rest is Apple's restore, which grows from ~0.67 s to 1.3–1.4 s as more 2 GiB guests come back into memory (probes/651-i345-WAKE-OFF-CRITICAL-PATH/RESULTS.md).
  • Tests: CI green; make test-vm twice (72/72), hardening concurrent (64 wakes at once), make test-vm-upgrade; the lifecycle, persisted-sandbox and boot-log suites locally.
