A site permission can name ports: site:HOST:PORT (issue #415; step 4 of the session-hub program, #405). From the peer's switchboard test on 0.40.0: site:<hub address> opened every port of the hub to a fenced session, and site:<hub address>:8780 matched nothing.

  • site:HOST:PORT and site:HOST:P1,P2 wherever site:HOST is taken: --permissions, --allow, doz net allow|deny (sandboxes and @mac --session), the dashboard. HOST is a name, *.domain or an IPv4 address; up to 16 ports. An IPv6 address is refused with the form to use.
  • What wins: a port allow opens only that port; a whole-host deny beats any port allow; a port deny blocks just that port under a whole-host allow. An old site:HOST rule still means every port — stored rules are read unchanged.
  • Allowing a port of a host you had denied whole lifts that deny, and the command says so (lifted: deny HOST).
  • Ports for one host are kept as one rule: site:H:80 then site:H:443 shows as H:80,443 in doz net show, the dashboard and --json (sites stays an array of strings).
  • A refused connection on a port other than 80 or 443 suggests the narrow grant, site:HOST:PORT.
  • Stricter on this Mac's sessions: --permissions site:localhost (and other undotted names) is refused now — one parser everywhere. It never opened anything: this Mac's own addresses and loopback stay refused whatever a site rule says, and tests prove it for site:127.0.0.1:PORT.
