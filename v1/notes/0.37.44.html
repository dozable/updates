Drive a session from a script, and a clear reason when the host cannot read your Claude login (issue #390). Owner 2026-11-12: "ship it to canary then prmote". Asked for by an agent that drives teams of Claude Code sessions in Dozable sandboxes.

  • doz sessions send SANDBOX SESSION types into a session from a script: --text (or --text - for stdin), then --keys (enter, tab, esc, arrows, ctrl-letter, f1–f12…), then --enter; --paste wraps the text in bracketed paste. It returns only once the session's holder has every byte, wakes a sleeping or hibernated sandbox first (--no-wake to refuse), and --then-screen[=MS] returns the screen after it in the same call. A missing or ended session exits 2; an off sandbox, 3.
  • doz sessions screen SANDBOX SESSION prints the screen as it is now — the rows only; --json adds the cursor, the size, which screen (primary or alternate) and the session's status. A sleeping sandbox gives its saved screen and says it is not live, waking nothing; --wake wakes it and reads it live.
  • A send into a hibernated sandbox wakes it and the text arrives — checked 5 times out of 5 — which a piped doz attach could not promise.
  • A host started over ssh says why it cannot read your Claude login. Over ssh the login keychain is locked, so a host started there gave every sandbox it made an "unreadable" account while doz doctor (run from the Mac's own session) said the login was fine. Now the host records its session: starting one there warns first; doz account ls, account show mac, doz ls and doctor's new "host login" check name that host (pid, start time) and say to run doz host restart from a logged-in session; doz image bake stops a host it had to start there once nothing runs.
  • Tests: make test-cli-sessionsend (20 checks, twice in a row), make test-cli-keychainlocked (8 checks), new unit suites, make test 1527 run / 0 failures, the audit and the docs checks. Still to come: sessions on the Mac itself (@mac).
