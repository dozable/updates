Open a sandbox's workspace in the Finder or your editor (issue #242; loop 627, step 11; backlog 614.B2). Owner 2026-10-11: an "Open workspace" action in the CLI and the dashboard, "in the Finder or an editor/IDE (VS Code, Cursor, Zed, Xcode …)"; 2026-10-24, after looking on doz-dev: "looks great".

  • Open folder, beside Open in Terminal on a sandbox's terminal strip: Show in the Finder, then Open in <editor> for each editor installed on this Mac — the one used last comes first. The Files tab's ⋯ on a folder or a file gains the same Open in <editor> items.
  • doz files open NAME [PATH] --app EDITOR opens the workspace (or a folder or file in it) in that editor; doz files editors lists what is installed. (doz open stays the command that opens a sandbox's web port.)
  • Which apps: a known editor that is installed (VS Code, Cursor, Zed, Windsurf, Xcode, Sublime Text, Nova, BBEdit, IntelliJ IDEA, PyCharm, WebStorm, GoLand, TextMate — found by its bundle id and opened by its own path, never by a typed name), or a name in bridges.open_apps.
  • What opens: a folder, or a file that is not a program — source files (.py, .js, .swift …) open in an editor though their default app is still refused (it could run them); an executable, a #! script, a Mac or Linux program and an app or package never open. The workspace rules come first (hidden is "no such file", locked is refused), and sandbox.open_files off refuses it. The agent's own opening is unchanged.
  • An isolated sandbox has nothing to open (the button says so); another device's browser (doz ui --lan) never sees it.
  • Tests: full make test 1239, 0 failures; make audit and docs-drift-check clean.
