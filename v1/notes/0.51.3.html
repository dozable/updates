Chat, steps 6–7: sessions, delivery into Claude Code sessions, attachments (hidden) (issue #442; chat loop 698). Still behind the hidden command; nothing here is visible to a user.

  • Delivery into a running Claude Code session, as the reference does it: the server finds the session by name in Claude Code's list of running sessions and writes the message to that session's own messaging socket; edit and delete notices and the protocol text go the same way; a message is marked started when the session turns busy after the hand-over; /react with no message named falls back to the one last handed to the sender. This is the first thing the chat server touches outside its own folder: it READS the session list and CONNECTS to the one session it delivers to; it writes nothing there and makes no socket of its own. Every test uses a scratch session folder and a scratch socket, and refuses to run against a real one.
  • Attachments: upload, inline bytes, attaching by id, download, and the line port's file line. Stricter than the reference on purpose: a file is served only to someone who may read a message that names it; a download carries nosniff and a sandboxing policy, and anything but the four common image types downloads rather than renders; an upload is capped at 20 MiB before a byte is kept; a caller's file name is never used as a path (files are stored under a random id).
  • Left out on purpose: attaching a file by its PATH on this Mac. A message must not be a way for a participant to have the server read files its own fence denies it; that is the owner's decision (one reference check stays out of the ratchet for it).
  • A message is found by the start of its id only when that start is made of an id's characters (an empty start, % or _ matches nothing), as the reference's 0.12.2 has it.
  • The gate: 159 of the reference's 185 checks pass (was 135), the same on every run. What is left is room apps (manifests, icons, the service worker) and that one check.
